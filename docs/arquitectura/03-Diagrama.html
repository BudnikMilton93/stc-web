Mapa del sistema — agosto 2026 (actualizado tras migración del frontend)

Cómo está armado STC hoy

Sistema interno de gestión técnica (clientes, sitios, órdenes de instalación). El frontend ya migró de hablar directo con Supabase a consumir la API en C# para todo dato de negocio — este mapa muestra el camino activo hoy y qué queda como legado/defensa en profundidad.

ruta activa hoy legado — ya no recibe tráfico del front frontera de seguridad
01 — visión general

Un solo camino de datos, un solo camino de sesión

El frontend autentica siempre contra Supabase Auth y, desde la migración, habla con Postgres solo a través de la API en C# — nunca directo. El acceso directo vía supabase-js con la anon key queda como camino legado, sin tráfico real del panel admin.

02 — stack

Herramientas por capa

Qué corre en cada punto del sistema, hoy.

Frontend

  • React 19 + Vite
  • React Router (rutas /panel-admin/*)
  • lib/apiClient.js — fetch + Bearer JWT (datos)
  • @supabase/supabase-js — solo sesión (Auth)
  • CSS propio, sin librería de UI
  • Vitest + React Testing Library (25 tests)

API

  • .NET 10 — minimal APIs
  • EF Core + Npgsql
  • JwtBearer (validación contra JWKS)
  • 3 proyectos: Domain / Infrastructure / Api
  • xUnit + Testcontainers (20 tests)

Base de datos

  • Postgres (alojado en Supabase)
  • Supabase Auth (login, JWT Signing Keys)
  • Migraciones versionadas con Supabase CLI
  • RLS: un solo usuario activo, sin roles

Entorno / conexión

  • Connection pooler (Supavisor)
  • Modo sesión, puerto 5432
  • Secretos vía dotnet user-secrets
  • Sin JWT secret — solo claves públicas (JWKS)
03 — seguridad

De un login a una fila autorizada

El recorrido que hace un pedido a la API en C# desde que el staff inicia sesión hasta que una query toca la base. Es la capa nueva; RLS sigue activa en paralelo para el camino directo del frontend.

RLS como defensa en profundidad: desde que el frontend migró a este camino, las policies RLS de Postgres (colapsadas a un solo usuario activo, sin roles) ya no son la autorización primaria — siguen activas por si algo llega a hablar directo con la anon key, pero el panel admin ya no depende de ellas.
04 — estructura de la api

Tres proyectos, una dirección de dependencia

Domain no depende de nada. Infrastructure depende de Domain. Api depende de los dos. Sin capa de "casos de uso" — con un solo usuario, la lógica vive directo en los endpoints.

05 — tests

Frontend y API cubiertos y en CI; falta RLS y e2e

La API tiene 20 tests de integración contra Postgres real; el frontend suma 25 tests unitarios/de componente. Ambos corren en .github/workflows/ci.yml en cada push/PR. Solo quedan pendientes las policies RLS y los flujos e2e.
